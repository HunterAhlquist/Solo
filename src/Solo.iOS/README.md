# Solo for iPhone, iPad and Mac — native client (experiment)

A SwiftUI client for a Solo instance. It talks to the same REST API and the same SignalR hub as the Blazor client in `src/Solo.Client`, so nothing on the server changes for it: point it at an instance and sign in.

It is an experiment and lives on its own branch. It is not part of `Solo.slnx` — it builds and runs locally, from Xcode or `xcodebuild` — and of the release train it has one part: a preview tag uploads the iPhone and iPad app and the Mac app to TestFlight (see "TestFlight previews" below).

## Running it

Requires Xcode 26 and an iOS 26 simulator or device, or a Mac on macOS 26 (the deployment targets are iOS 26 and macOS 26, for Liquid Glass).

```bash
open src/Solo.iOS/Solo.xcodeproj
```

Choose the `Solo` scheme and an iPhone or iPad destination, or **My Mac**, and run. The packages resolve on the first build. The one target builds for all three; the Mac's is a native app (AppKit under SwiftUI), not the iPad's running on a Mac — that way of running it is switched off.

On first launch the app asks for the instance's address, then signs in through the instance's own sign-in page in a system sheet. It keeps the session token in the Keychain and the instance in its settings, so later launches go straight in. More instances can be added beside the first — see [Several instances](#several-instances).

The tests are in the `SoloTests` target (`⌘U`, or `xcodebuild test`), and run on a simulator or on the Mac. They cover the rules the app has to share with the server and the web client — dates, serial numbers, rank neighbours, the roadmap's sprint arithmetic, note addresses and heading slugs, the Design Docs sync batch format, the sketch rasterizer against values taken from the web one, and the About window's game against games played on the desktop shell's.

### The Mac download

Every release tag also attaches the Mac build to its GitHub release, as a disk image anyone can download and open: `Solo-<version>-mac.dmg`, or `Solo-Preview-<version>-mac.dmg` for a prerelease. It is the `mac` job of [release-desktop.yml](../../.github/workflows/release-desktop.yml), beside the Windows and Linux installers, and it is the same target the Mac TestFlight upload builds, signed differently: that one is the store's and opens only through it.

- **Signed by `build/package-mac-direct.sh`.** The archive is signed for nobody, as for the store. The script signs the app with the Developer ID Application certificate and the hardened runtime, keeping the sandbox entitlements it was built with and adding none: a Developer ID app has no provisioning profile, and the app asks for nothing that needs one — its session is in the login keychain. Apple notarizes the app, the ticket is stapled to it, and only then is it put in the image with a link to `/Applications`; the image is signed, notarized and stapled in turn. So the app carries its own ticket once it is dragged out, and both open on a Mac that can't reach Apple.
- **The secrets are the shell's.** `MAC_CSC_LINK` and `MAC_CSC_KEY_PASSWORD` (the certificate, a base64 .p12), and `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` for the notary service: the repository's own, which signed the Electron shell's Mac build. Without all of them the job says so and the release has no Mac download: unsigned or un-notarized, Gatekeeper turns the app away.
- **Which app it is.** A prerelease is built as the TestFlight preview is — `com.hunterahlquist.solo.preview`, "Solo (Preview)", the preview icon — so the downloaded preview and the TestFlight one are one app come by two roads, and share what they keep. A release is the project as it stands: `com.hunterahlquist.solo.native`, "Solo", its own icon. That is not the store app's bundle id, which the repository doesn't hold; given it, the release could be made the store's app in the same way.
- **Built for every tag, and in no feed.** Nothing points from one release at another's image, so each release gets its own. It is kept out of the updater feeds and the manifest, which are the Electron shell's: the app does not update itself, and an installed copy of the shell is not told about it.
- **It needs macOS 26**, as the app does, and is universal.

This was run here in full, on an archive built from a clean copy with the preview identity: signed with the real certificate, accepted by the notary service twice, stapled, and taken by Gatekeeper as "Notarized Developer ID", the app and the image both. A copy signed the same way under the project's own id was opened and showed its instance, signed in from the keychain. The job itself — the certificate from the secret, the notary's credentials — is first run by the next tag.

### TestFlight

A release tag uploads the app to TestFlight, to one of two App Store Connect apps: a `preview-v<version>` tag to the preview app, and a version tag (`v<version>`) to the store app. The preview is described first; what a version tag does differently is at the end.

A `preview-v<version>` tag uploads the app to TestFlight for internal testers, twice: the iPhone and iPad build ([release-ios.yml](../../.github/workflows/release-ios.yml)) and the Mac build ([release-mac-store.yml](../../.github/workflows/release-mac-store.yml)), each from the Capacitor port's workflow of the same name. Both are built as the preview app — `com.hunterahlquist.solo.preview`, "Solo (Preview)", with the preview icon from `Icons/` — which is the App Store Connect app the earlier previews went to, the Capacitor app on iOS and the Electron shell on the Mac, so testers get this one as an update to the one they have.

- **The tag is the whole train's.** The same tag runs `ci.yml` and `release-desktop.yml`, which publish the server image, the extension packages and the desktop installers as a prerelease from the tagged commit ([docs/prereleases.md](../../docs/prereleases.md)). There is no tag that uploads the app alone, and the `testflight` environment that holds the App Store Connect key only deploys from the tag patterns its own rules list (Settings → Environments → testflight), so a manual run from a branch stops at that environment — and so does a tag whose pattern isn't listed there, before any step runs.
- **Not every preview tag uploads.** `build/testflight-gate.sh` compares `src/Solo.iOS` (its README aside), `Icons/`, `build/release-channel.sh` and the workflow against the commit of the last run that uploaded, and skips the build when none of them changed. Each platform is compared against its own workflow's last preview upload: a version tag's run went to the other app, and is passed over.
- **Identity is given on the command line.** The project builds as `com.hunterahlquist.solo.native`; the workflow passes `SOLO_BUNDLE_ID`, which the app, its widgets and its tests each make their own identifier from, along with the display name, the icon's name, the version from the tag and, on iOS, the team. No team is written into the project. The build number is the UTC minute of the build.
- **On iOS, signing is Xcode's, with the App Store Connect key.** The archive is signed with a development certificate the run creates and then revokes (`build/asc-revoke-run-certificates.swift`); the export re-signs for distribution and uploads, marked internal-only (`ExportOptions-testflight.plist`).
- **On the Mac, signing is the environment's certificates.** The archive is signed for nobody; `build/package-mac-store.sh` then signs it with the Apple Distribution identity and the Mac App Store profile the `testflight` environment already held for the Electron preview (`MAS_CERTIFICATES`, `MAS_PREVIEW_PROVISIONING_PROFILE`), adds the two identifiers TestFlight needs to its sandbox entitlements, and wraps it in a package signed with the installer identity, which `altool` uploads. It installs as "Solo (Preview)" in `/Applications`, where the Electron preview was, beside a downloaded Solo rather than over it. The script signs one binary: when the Mac build gains an extension or a framework of its own it stops and says so.

**A version tag goes to the store app.** `v<version>` builds the same target as "Solo", with the project's own icon, and uploads it to the app the `testflight` environment's `SOLO_ASC_APP_ID` variable names — that app's Apple ID, under App Information in App Store Connect. The variable is the only place the app is named. An upload is filed by bundle id, so each job asks App Store Connect for that app's bundle id (`build/asc-app-bundle-id.swift`) and builds under it; pointed at another app, the next tag is built for that one, and pointed at the preview app it is refused. What else differs:

- **It always uploads.** There are few version tags, each is a release made on purpose under a version the store app hasn't had, and the gate isn't asked.
- **It lands with internal testers, and can go further by hand.** The preview's iOS export is marked internal-only (`ExportOptions-testflight.plist`), a mark the build keeps for good. A version tag's is not (`ExportOptions-store.plist`): its build can be added to an external group, which sends it to Beta App Review, or chosen for an App Store submission. Neither is done by the workflow; both are steps taken in App Store Connect.
- **The Mac build needs a profile of its own.** `MAS_PROVISIONING_PROFILE`, a Mac App Store profile for the store app's bundle id, beside the preview's `MAS_PREVIEW_PROVISIONING_PROFILE`; the certificates are the team's and serve both. Without it, or without `SOLO_ASC_APP_ID`, the Mac job says what is missing and skips, and the iOS job is unaffected. It installs as "Solo" in `/Applications`.
- **The environment has to let the tag in.** Its deployment rules need a `v*` tag pattern beside `preview-v*`.

Preview tags have uploaded both builds many times. The version-tag path has not run: what was checked here is that both workflows parse and lint, that their steps choose the right app, variable and profile for each kind of tag and skip with a notice when something is missing, and that the bundle-id lookup signs its token and reaches App Store Connect, which refuses a made-up key as it should. The answer to a real key, the store app's signing and the upload itself are first tried by the first version tag.

### Debug hooks

Debug builds read three environment variables, which is how the app was driven on simulators without typing a Google password into one:

| Variable | Effect |
|---|---|
| `SOLO_INSTANCE_URL` | The instance to use, skipping the address screen. |
| `SOLO_SESSION_TOKEN` | A `solo_…` session token to resume with, skipping sign-in. |
| `SOLO_OTHER_INSTANCE_URL`, `SOLO_OTHER_SESSION_TOKEN` | A second instance, kept beside the first and signed in the same way, to switch to. |
| `SOLO_OPEN` | Where to start: a tab (`work`, `projects`, `inbox`, `account`), a project (`DMD`), a board (`DMD-PW26`), a task (`DMD-PW26-2`), `roadmap:DMD:<id>`, `docs:DMD:<vault id>[:<note id>]`, or `route:<mcp\|admin\|devices\|notifications\|extensions\|themes\|users\|email\|updates\|about>`. |
| `SOLO_PERF` | Writes a line a second to `Documents/perf.log`: frames drawn, the longest wait between two, how much of the second was spent late, and how many zones and cards were built. |
| `SOLO_PERF_SCROLL` | With `SOLO_PERF`, a speed in points a second: once the screen has settled the app scrolls its longest page down at that speed and back up at three times it, and the log says where it is. The same swipe every run, and the only way to scroll a device from here. It also keeps the screen awake. |

The instances these were pointed at while the app was written are two entries in `.claude/launch.json`, `solo-native-api` on port 5155 and `solo-native-api-2` on 5156: this checkout's server, built first (they run it with `--no-build`), on the local dev database's `solo_native` and `solo_native2`, listening on every interface so a device on the network can reach them. The first loads whatever extension packages are in `artifacts/native-ext`, a folder git ignores — the first-party ones from a build, and `Spikes/NativeKit/pack.sh artifacts/native-ext` for the test plugin.

With `simctl`, prefix each with `SIMCTL_CHILD_`; for the Mac's build, `open -n Solo.app --env SOLO_OPEN=…`. The perf log is written on a Mac too, to `Documents/perf.log` in the app's sandbox container (`~/Library/Containers/…/Data/Documents`), and the Mac's window has to be in front for the run, since one that is covered is not drawn at its full rate. None of this is compiled into a release build — unless it is built with `PERF` among its compilation conditions (`SWIFT_ACTIVE_COMPILATION_CONDITIONS='$(inherited) PERF'`), which is how the app is measured optimised: a debug build's timings say little about a release build's.

## How it is put together

```
Solo/App          app entry, launch states, the signed-in Session, the Navigator
Solo/Core         API client and endpoints, models, auth, the live hub, theme, stores
Solo/UI           shared pieces: markdown, images and icons, cards, prompts
Solo/Features     one folder per area of core: board, dashboard, projects, inbox, account, admin
Solo/Extensions   the first-party extensions' clients, and the slots they fill
SoloWidgets       the Home Screen widgets, an extension of the app
SoloShared        the little the app and its widgets both compile: what they share, and its shape
SoloTests         unit tests
```

- **One navigation model, two shells.** `Navigator` holds a tab and a stack of routes per tab. An iPhone shows it as a tab bar; an iPad as a sidebar beside the selected stack, with a task's detail in a panel down the trailing edge — three panes in landscape. Routes are aliases, as the web app's URLs are, so a link means the same thing on every client. A phone's screen wide enough for the sidebar's shell — a folding iPhone opened out, a large one on its side — has it too, but with the sidebar slid over the page and not beside it (`SplitShell.slidesOver`): there is no room there to give the sidebar without squeezing the page. It is put away once it has been used to go somewhere. Which it is is told by the window's shorter side, not by the kind of device (`panesFloat`).
- **The task panel is the shell's.** On an iPad it is not the system inspector, which sits inside the page's navigation stack — under the bar, with the page beside it snapping to its new width. `DetailPanelCenter` lets a page hand its panel to the shell, which draws it as a pane of glass over the bar's trailing end; the page makes room through its safe area, which animates.
- **A phone's board is one page.** The three columns are not three scroll views. Every row — an epic — holds its three zones side by side and shows the one the page's column names (`PagedColumns`), so a row is at the same height and under the same header whichever column is showing, and a sideways drag anywhere turns all of them together. A card that changes column is followed there and centred.
- **A big board is built a lane at a time.** The page is a lazy stack whose rows are lanes, and a group of epics is its title and then each of its epics as a row of its own (`BoardRow`), with the group's outline drawn in pieces that meet — a group used to be one row, so opening a board built every epic of its first group. Two layouts keep the page from being measured more than once: `ZoneRow` gives a lane's three zones a third of the width each without asking them how flexible they are, and `FillLayout` stops the bars around the page from asking the scroll view how tall all of its content is, which a lazy stack can only answer by building rows. The board's tasks are sorted out by lane and column once each time the board changes (`BoardIndex`), not once for every zone drawn. Your Tasks builds its cards as they scroll into view; on a phone a column that a card has just been moved to is built whole, so that the page can go to the card. On the test board of 580 tasks in an optimised simulator build, opening went from one frame of 940 ms and nine lanes built to 180 ms and two; Your Tasks at launch from 830 ms and every card to 180 ms and the ones in view. Within a lane, each zone builds its cards as they scroll into view too, and draws their glass in one `GlassEffectContainer`. That came from measuring on an iPhone Air, with the app scrolling itself (`SOLO_PERF_SCROLL`) down the same board at 1,000 points a second: with every card of an arriving lane built at once and a layer of glass each, the phone held 112 frames a second out of 120 while cool and about 60 once it reported its thermal state as fair, which a few minutes of use is enough for. Lazy zones alone gave 92 warm and the container alone 83; together 110 to 120, warm or cool. A container is only used for a zone of up to 30 cards: around a column as tall as one of Your Tasks' it halved the frame rate instead, so Your Tasks has none. What was not measured: an iPad, and what the render server does with the glass — the log only sees the app's own main thread, and the hitch recorder in Xcode could not reach the phone over Wi-Fi.
- **A big board on a Mac.** The same board, measured the same way on a Mac — the perf log and the scroll run there too, an optimised build scrolling itself down at 1,500 points a second and back up at 4,500 on a 120 Hz screen — held 98 frames a second going down and 71 coming up, each lane arriving as one frame of 30 to 40 ms. Nothing on the main thread was drawing: it was all building and measuring. The lanes were not it (with a card that was only its title the page held 118), so each part of a card was switched off in turn. Two stood out, and both are a Mac's alone. The button around each card cost more than the rest of what a card is wrapped in put together, so on a Mac a card is pressed with a click and tells assistive technology it can be (`pressToOpen`). And glass with a tint, cut to a shape of the app's own, cost more than plain glass in the system's rounded rectangle, so there the wash is laid over plain glass (`CardGlass`), which looks the same. With both, 109 going down and 85 coming up, with about half the time lost to late frames. What is left is spread thinly over everything else a card has — its label, its rings, its faces, its menu, the Finished fold — none of it more than two or three frames by itself. Opening a task beside a big board is not smooth either, and is not changed by this: the page gives the panel room over 0.38 s, and every frame of that lays out every lane showing again at a new width.
- **Finished is held to what is left to do.** As on the web (`KanbanZone.razor`, `js/finished-column.js`), and to the same numbers: a Finished column's cards may stand as tall as the lane's active columns, or 340 points where those are shorter, and no taller. Past that they scroll inside the column, and a column that has to scroll starts put away behind "Show finished (17)", so a lane is as tall as the work left in it; past 25 cards the rest fold behind "Show all". It is one component, `FinishedFold`, on a board's lanes and on Your Tasks. Three things are the app's own. Cards put away are not built, so whether they would fit is judged by the last time they were, or by a guess from the cards beside them, where the web keeps them laid out and hidden. A column that scrolls does not bounce, so that a drag past its end goes on to the page: on a phone the column is most of the screen. And a card dropped on a column that is put away still lands in it, where the web takes no drops there. The active columns' heights are kept in `LaneHeights`, which only the Finished column observes — as the lane's own state they had every column of the lane worked out again a hundred times a second while scrolling.
- **What is picked up is carried.** A card, a lane or a group of lanes that is pressed and dragged is in hand as itself — the same size, a little raised, where the finger took hold of it — and what it is carried over parts to leave it room, which is where it goes when it is let go (`CardDragWatch`, `CarriedCard`, `SlotGap`). The drag is the system's, so a card can still be let go on a column of the selector, held at the page's edge to turn the column, or taken to another app; the system is handed a preview of nothing, since what it would show is the thing shrunk. While a lane is in hand every lane is folded, and every group too while a group is, so that it is carried over a short list of names; the page opens again once it is put down, and goes to it. A lane is put in a group by being let go among its lanes, or level with its last one. Your Tasks carries its cards the same way, with the same pieces, though a card there is only ever put in another column and no room is made for it among the cards: where it lands is its board's to say. Four things are not as they would first be written. What is in hand is learned from the name its item provider carries when it first arrives over somewhere it could be let go, and not from the system asking for it: the system asks at a press that goes on to open a menu, and does not ask again for the next press on the same card. The places a card is let go are the zones, and for a lane the page — never the cards or headers it goes between, which are moving out of its way at that moment, so that a finger placed by one of them was a frame out and the thing in hand shook. And which gap the finger is over is judged by the middles of the rows as they stand with the room open, so that opening the room does not change the answer. And the card left behind while one is in hand — it has to stay, since the system carries the drag by it — is put far off to one side, because the system keeps a picture of what it lifted and draws it wherever the card is, whatever is said of the card's opacity. The system moves that picture at whatever pace is going when the card moves, so picking up and giving back are each two steps: the swap of the card for the one drawn in hand, with no animation at all, and a moment later the place closing or opening at its own pace. Done as one, the card was seen flying off the screen as it was picked up and flying back in as it was put down. Where a card stands is kept by the column it was built in, since a card that changes column is for a moment built in both, and the copy on its way out goes on saying where it is. And a thing is not always said to have been let go: within a few points of the screen's edge the system says nothing at all, neither that it was let go nor that it left, which on a phone is exactly where a card is held to turn the column. While a thing is carried the system says where it is many times a second, moved or not, so once it has been heard to repeat itself a silence is taken for the thing having been let go (`CardDragWatch.alive`): on an edge or a column of the selector it is let go there, and anywhere else it is given back. A card let go on an edge goes to the foot of its lane in the column beyond that edge. A Mac differs in two of these. A place is handed a provider made afresh from the pasteboard there, with the text and not the name, so what is in hand is read from the pasteboard the drag is carried on. And a Mac always says when a thing is let go, so silence is not listened for; what it does not always say is that a drag was given up — Escape, or let go over another app — so while a thing is in hand the mouse's button is looked at, and up, the thing is given back.
- **Live by default.** `HubClient` joins the board, user and extension topics the web client joins; stores apply what arrives. Saves send the row's `version`, and a 409 refreshes and says so. A page kept live this way — a board, Your Tasks, the inbox, a roadmap — has no pull to refresh, which would only fetch what it already has. The pages that are read once when they are opened still have it: the project lists, a project's page, the admin and account lists, and an extension's page.
- **Offline is its own, smaller window.** The last good response to every GET is kept on disk, so a page whose request fails still shows what it last showed, and the app opens signed in with no connection. But nothing so shown can be changed, so once the instance is known to be out of reach — a request failed, and so did asking it whether it is there (`Session.offlineMode`) — the window shows only what can be: the design docs downloaded to the device (below). The sidebar becomes a list of them under a line that says the instance can't be reached and a button to ask it again (`OfflineMode.swift`); the page is one of them or a page listing them; an iPhone, with no sidebar, has that page and no tabs; a Mac's Go menu has nowhere to go. A link out of a note to anything else is refused, and says why. A design doc that was open when the connection went is not rebuilt or moved, so what was being written goes on being written; any other page is kept where it was and comes back when the instance does, which is asked every eight seconds, when the device's own connection changes, when the live feed drops, and when the app comes forward. The mark in the bar that used to say "offline" is gone — the window says it — and what is left there is the one for the live feed reconnecting. Outside a downloaded design doc nothing is queued; the one exception is a note or sketch that is open, which keeps unsent edits and sends them when the connection returns.
- **A design doc's tree is on the trailing side.** Beside a note on an iPad and a Mac, the note tree is a panel down the trailing side of the page. The leading side is the app's own sidebar's and its button's: with the tree there too the two stood side by side. The tree's button is in one place, the trailing corner of where the panel stands: at the head of the panel while the tree is out, and by itself on glass there while it is away, as the app's sidebar's button keeps to its corner. It is the trailing sidebar symbol, since the leading one is the app's sidebar's. That button and the two beside it at the panel's head are circles of glass the size of the bar's own button for the sidebar (`PaneButton`): 44 points on an iPad, 48 on a phone, 36 in a Mac's window. On a phone's wide screen, where there is not room for a note and a pane beside it (`panesFloat`, the rule the app's sidebar goes by too), the tree goes over the note, which keeps its width and passes behind it; there it starts put away, and is put away again once a note has been picked from it. On a phone's narrow screen a note is a page of its own and Back is the way to the rest: a note come to from anywhere else — a link in a task, a notification — is given the design doc's list of notes to go back to, between it and where it was come from, and the list is taken away again if the screen is opened out wide, where it is on the note's own page (`settleWhatIsUnder`).
- **A theme's picture is the main window's alone.** Every page draws its own background (`AppBackground`): the wash, and over it the picture a theme puts behind the app. What a page draws is said by where it is (`Backdrop`). In the main window it is both. A cover — a sketch, a picture — and on a Mac the windows beside the main one, Settings among them, draw the wash and no picture. A sheet draws nothing, not the wash either. On an iPhone or iPad it is a pane of Liquid Glass, said outright because a sheet at its full height is otherwise given a solid ground, and the page it rose over shows through it, bent; on a Mac it is the sheet's own plain ground. Every sheet comes through the app's own `sheet` (`Components.swift`), which is where this is said once for all of them; a cover says it where it is presented (`withoutBackdropPicture`).
- **A note is read on a ground of its own.** Behind a note's text is the page's white or black at three quarters (`NoteGround`), so that a theme's picture is quiet behind the words. It is whole across the column of text and fades away on each side, gone by where the app's sidebar and the design doc's tree come to when they are out — whether they are or not, so that putting one away does not move it — and where the column already reaches that far, over a short way past it, under the pane's glass. A phone has neither beside a note and is covered from side to side. The column is laid out and the ground drawn by one rule (`NoteColumn`): as wide as reads well and no wider, centred in what can be seen of the page, since a note passes under the app's sidebar.
- **A note's text size and margins are its design doc's.** The web's two menus over its editor (`DesignDocsPage.razor`), with the same choices: text at 75 to 200 per cent of the size it is otherwise written at — which on an iPhone and iPad is Dynamic Type's, so the two multiply — and margins left to the column's measure or set to none, 5, 10, 15 or 20 per cent of the note's width on each side (`NoteLayout`). They are in the note's menu in the bar, and in the page's menu on a phone, each row saying what it is set to; on a Mac the size is also in the View menu, on ⌘+, ⌘− and ⌘0. As on the web they are kept for each design doc on the device and not on the instance (`js/preferences.js`), so a phone and a Mac can differ. The size is the styler's (`NoteStyler.scale`): everything in a note is sized from its body text, so headings, code, checkboxes and the space between lines follow, and a row of pictures is drawn to it as the web's is (`--design-docs-scale`). The margins are the column's (`NoteColumn.margin`), a share of what can be seen of the note between whatever stands over its sides, and the note's name and its ground keep to them. The note's name is not made bigger or smaller.
- **A note is renamed where its name is.** The name at the head of a note is the biggest thing in it, and a field (`NoteTitle`): a click or a tap in it starts writing, and Return, the keyboard's Done or leaving the field gives the note the new name; Escape on a Mac leaves it as it was, and so does emptying it. It goes through what renaming from the tree goes through: other notes link to a note by its path, so where any do, that is said first, and turned down, the head goes back to the name the note has. To someone who may not write in the design doc it is only the name. The design doc itself is renamed from its row on the project's page; its bar has no pencil, which over a note read as renaming the note. The head is a SwiftUI view the editor lays over the top of its text and sizes when the note's view is drawn, so what is being written is kept by the note's view (`NoteView.title`) and read there: a name that grows onto a second line is given the room, and the text moves down. Where the design doc's tree is put away and its button stands by itself over the note's corner, a head that reaches that far is kept short of the button (`headClearance`).
- **A design doc can be downloaded.** As on the web (`js/offline/session.js`), and over the same endpoints (`…/vaults/{id}/offline`): the cloud in a design doc's bar brings every note, sketch and picture in it onto the device (`OfflineDocs.swift`), and from then on its notes and sketches open and are written in with or without the instance. An open document's changes are kept on the device first and owed to the instance, and are no longer sent over the live connection, though what others write still arrives over it; what is owed is paid whenever the instance can be reached — when a change is made, when the connection returns, when the app comes forward, and every ten seconds between. Each document is kept twice, as it stands here and as the instance is known to have it, and what is sent is the difference, under an id that is kept until it is answered: the instance answers a repeat with the answer it gave the first time, so an update that arrived and was never heard of is not sent as a second one. The rest of the design doc — its tree, its lists of sketches and pictures — is read through the app's ordinary requests, whose last answers already stand in when the instance is out of reach; the download asks them again whenever the design doc has changed, so that what they keep is the design doc as downloaded. What is done to a downloaded design doc's tree is done on the device first as well (`OfflineChanges.swift`, after the web's `applyCommand` and `projectVault`): a note or a folder made, renamed, moved or deleted; a sketch made, repapered or deleted; a picture added, replaced or deleted; the design doc renamed, closed or deleted, or a new one made in a project that already has one downloaded. Each is written down as a command, and the design doc is shown as the instance last had it with the commands still to send laid over it, so it shows at once and with the instance out of reach. They are sent in the order they were made (`…/offline/commands`), before any document's changes, since a note has to be there before what is written in it can be. A deletion names every row it takes with its version, and how far each document it takes had been read, and the instance refuses it if any has moved on; a rename or a move is refused if the thing was renamed or moved by someone else meanwhile. What the instance makes of a command is taken as the truth of it — a name it had to change, a place it stored a sketch other than the one expected, in which case the notes that embed it are pointed there. The cloud says how the design doc stands: in step, with something to send, or with a change the instance refused, which is kept and listed. A refused change to a document can be sent again as it is or given up; one to the tree is done again to the tree as it now is, or given up — except a deletion, which is to be made again knowingly. A download can be removed once nothing in it is owed. Everything of a download that is on the device can be taken away as a zip (`OfflineRecovery.swift`, after the web's `js/offline/recovery.js`), from the cloud's menu and from the list of refused changes, where it is what to do before giving any of them up: each note as a Markdown file under its folders, each picture where it is stored, each sketch drawn as a PNG beside where it is stored — and its embeds in the notes pointed at that — and `solo-recovery.json`, with every document as Yjs has it here and everything that was still to send. The notes are as they stand on the device with what is still to send laid over them, so one made here and never received is in it, and so is one the instance has deleted since: a document that goes from the instance is kept on the device until the download is removed, with the row that named it. What the web's has and this has not: importing notes into a downloaded design doc. What is downloaded is kept in Application Support, apart for each instance and person, and is not removed by signing out.

The app is one window, as it is one session looking at one place; it is sandboxed, and keeps its session in the login keychain. A window can be far narrower than an iPad, which an iPad's layout does not expect: it is held to 960 points at the least, the task panel takes a third of it and not two fifths, and where the sidebar, a board's three columns and the panel are more than it holds, the sidebar gives way while the panel is open and comes back when it closes (`SplitShell`) — kept between launches, since the window remembers its sidebar was away and would not say why. A Mac's build has no widgets and plays no haptics.

The commands for the selection hang under the selected bars there rather than sitting at the foot of the page, which is where a thumb wants them and a pointer does not. The app has one `ToastCenter` between its windows, so a toast is said in one of them: the window in front when it was raised — a sheet or a popover counting as the window it hangs from — or, with none in front, the last that was, and failing that the main one. Each window's `ToastOverlay` tells the centre which window it is in and when that window comes forward.

- **Accent as a fill.** The instance's accent is whatever the theme says, and may be a bright yellow. Where the app draws on it, the label is black or white by contrast — set on the label, since a prominent button's style overrides one set on the button. Where the system draws white on it and gives no say (a switch's knob, a swipe action's icon), the fill is the nearest shade of the accent that white reads on. The app's own accent, worn before an instance's theme is known, gets the same working out: it is a bright yellow in the dark, and Connect was white on it. Its two colours are kept as numbers beside the asset catalogue's `AccentColor`, and a test holds them together.
- **First run.** A launch with no instance, by someone who has never connected to one, opens on two screens before the one that asks for an address (`Features/Onboarding/Onboarding.swift`): a welcome, and what an instance is and where it can run, with a link to the docs' install page. "I have an Instance!" is remembered (`solo.onboarding.seen`), and "Restart Onboarding" on the connect screen forgets it. Anyone with a recent address skips straight to connecting. The three screens are a row — each as far from the next as the screen is wide, the space beside a camera included, so that the next one's edge doesn't show in it — moved a frame at a time by one clock (`OnboardingGuide`) that the 3D over them and the face are placed by as well, so the three keep step: what RealityKit draws is not carried along by a SwiftUI transition. `SOLO_ONBOARDING=welcome|hosting|connect` opens a debug build on one of the three with whatever it has kept left alone, and `SOLO_ONBOARDING_PACE=10` slows the slide between them for looking at it half way.
- **The face** goes through the first run with whoever is having it. On the welcome it is by the mark, smiling. On the next screen it comes down to the corner over the words, which are a speech bubble pointing at it and start empty: it says them a letter at a time, its mouth going, stopping for breath at commas and full stops, and a tap on the bubble has the rest at once. Where there isn't the height for all of it (a phone on its side, or large text) the bubble is still whole and the words scroll inside it, kept at the one being said. When it has finished it waits, and blinks every few seconds, not to a beat and now and then twice. It does not slide from one place to the next but goes there (`OnboardingGuide.flying`): it lifts off, crosses on a curve and comes in from above, a little nearer the eye half way than at either end, turned toward where it is headed and leaning into it, and its weight carries it a touch past its place as it lands. It takes about one and three quarter times as long over that as the screens take to change, so it sets off with them and comes down just after they have stopped, and only then starts to speak. Going to the connect screen it smiles, comes to rest beside "Restart Onboarding" at the button's height, lying down flat onto the page as it goes, and a picture of it takes its place. It is drawn in Aseprite, and that drawing is all there is of it: `Solo/Features/Onboarding/Models/SoloGuy.aseprite`, sixteen points square, its frames tagged `Smile`, `Idle` (eyes open, then shut), `Talk` (mouth shut, then open) and `Tap`. The last is the face it makes at being handled: taken hold of or dragged about, it wears it, and goes on wearing it for two seconds after it is let go — counted again from the last time if it is taken up again first — and then goes back to what it was doing. It does not break off talking for it. The picture of it beside "Restart Onboarding" does the same when it is pressed. The app reads the file itself (`Guy.swift`) and makes the 3D face by raising each frame's outline off the page — one solid per part of the face, with the drawing's own edges, not a block for each point — so changing the drawing changes the face, with nothing to export. With Reduce Motion the words are all there from the start and the screens change without the slide.
- **The 3D models.** The first run's models are on one RealityKit stage (`Stage.swift`): the mark in pieces, a server, a cloud and an old laptop round Docker's symbol, which is drawn flat with its arrows, and the face. The models are made in Blender. Their sources are `Models/SoloLogo.blend` and `Models/Hosting.blend`; what the app carries is each one exported to `Solo/Features/Onboarding/Models/*.usdz` by `Models/export_usdz.py` (`blender -b Models/SoloLogo.blend -P Models/export_usdz.py`), so after changing a `.blend`, export it and commit both. `SoloLogo.blend` is exported a second time, as `site/assets/models/SoloLogo.glb` by `Models/export_glb.py`, for the documentation site's front page, which shows the same mark with the same springs and glass (`site/_hero/hero-logo.js`); a change to it means running both exports. The app finds parts by their Blender object names (a test loads both files and looks for them), repaints the ones that are the accent or change with the scheme, and leaves the rest as the file has them. Each piece is a dynamic physics body with no gravity, pulled toward its place by a spring and toward a finger while one has it, so a piece dragged into another pushes it instead of passing through; each group is its own physics space, which is what lets the whole thing turn. The stage is one view the size of the screen, over all three screens, that is made once and never moved, hidden, reordered or made again: each screen leaves room where its models go and says where the room is, and the stage puts them there every frame, as far to one side as the screen itself has slid. It takes no touches; a screen passes on the ones in its room, and the stage finds the piece under the finger itself. It is one view because every other arrangement failed, each in its own way. A stage that is off to one side, waiting for its screen, holds up the drawing of everything else: the welcome ran at about one frame a second with the next screen's stage beside it. A stage with the glass pass that is taken out of the window and put back, or only moved in front of or behind something, goes on being drawn and is never shown again. And one made as its screen slides in isn't drawn until the slide has stopped. So there is one, and if it is ever taken down in a run of the app — the first run left and come back to — the screens are shown flat from then on: the app's icon for the mark, symbols for the models, and the face as its picture. Its size may change, and its picture is made again to fit, with one exception: when the device is turned the picture stays the shape it was, tall in a wide view, with everything on it in the wrong place. Any later change of size puts that right, so the pass tells the stage what size it was handed to draw on, and a stage whose picture has been the wrong shape for a few frames has its view made a point narrower and back until it isn't (`StageRig.fit`). Two more that were found the hard way: the stage is lit by a painted environment and not by light entities, which light nothing in a second stage made while a first is on screen; and it is never rebuilt for a change of colour scheme, which the system makes and unmakes as the app goes to the background.
- **Glass.** The logo's bars are the icon's glass, with its numbers (`Icons/Solo.icon/icon.json`): each layer's fill and opacity, and the group's refraction. RealityKit has no material that refracts and its shaders aren't shown the frame, so the glass is made in a post-process pass (`GlassLens.swift`): the bars are in the scene as their shine alone, and the pass follows each line of sight through the bars it meets, laying each one's colour and bending the line for what is behind, before reading the frame where the line ends up. It knows the bars as geometry — rounded slabs, posted each frame — not as a picture. The face is also a lamp. A point light goes with it, a little toward the eye (`Guy.swift`), and lights everything solid on the stage; so that its light falls across their fronts and not along one edge, the mark and the hosting models stand back from the stage's plane (`StageScene.back`) and are made larger by as much as that would make them smaller, which leaves them where and as big as they were with the face in front of them. A light entity works here, on the one stage; it was a second stage's lights that lit nothing. The glass is the pass's and not the scene's, so the pass lights it itself from the same place: its face brighter in its own colour toward the lamp, its rim taking the light in on the near side and letting a little out on the far one, and through it the lit tile behind, bent as before. By day the lamp gives about a third of what it does in the dark, since it is the accent's colour then and at full strength laid that over everything. The same pass gives the face its glow, there being no bloom to ask for either: the face's material gives off its own colour, and the pass takes the part of the frame the face is in, keeps what is that colour and inside the face's own box — what the face lights is as bright as it and is not it — blurs it in a small picture and lays it back. To keep it cheap the frame is copied across whole and the shader run only over the box the glass fits in and the box the glow reaches (on this Mac's GPU, at an iPhone's frame size, 0.04 ms for the glass against 0.08 ms when it ran over every point, and 0.06 ms with the glow). `GlassPass` is the pass apart from RealityKit, and the tests run it on frames of their own, which is also what says the shader compiles: it is compiled from a string at run time, so the project needs no `.metal` file and no Metal toolchain to build, and where it can't be compiled the bars stay plain tinted glass and the face has no glow.
- **Docker's symbol** is Docker's own drawing, from its brand guidelines (docker.com/company/newsroom/media-resources), kept as `DockerSymbol` in the asset catalogue. It is used as they ask: the symbol alone and unaltered, in their light colour on a dark ground and their dark colour on a light one, with half its width left clear on every side (a test holds the arrows and models outside that).

An iPhone won't hand one over (`UIImage(named:)` asserts on an Icon Composer icon), so the app carries a picture of each, `AppIconArtwork` and `AppIconArtworkPreview`, rendered from the `.icon` files by `src/Solo.Desktop/scripts/build-icon.mjs` along with the web's icons; run that again after changing an icon.

## Extensions

On the web an extension ships its client as an assembly the browser downloads. An app can't load code, so the three first-party extensions' clients are compiled in, under `Solo/Extensions`, and each is switched on only when the instance reports that extension (`GET /api/extensions`). An instance without Roadmaps shows no roadmap anywhere, exactly as its web app does; the catalog is read again whenever the live feed reconnects, since a restart is when it can change.

Core never asks about a particular extension. It names slots — sections of a task's detail, of a project's page and card, of the sidebar, of Your Tasks, of the Markdown editor, of admin settings — and `ExtensionSlots.swift` fills them.

| Extension | What is here |
|---|---|
| **MCP** | The MCP Access page (token, client snippets, tool list, usage) and a task's "Work for an LLM" switch. |
| **Roadmaps** | The timeline with press-and-hold to move and resize, milestones, sprints, the personal roadmap on Your Tasks, and the project, sidebar, card and task sections. |
| **Design Docs** | Design docs and their tree; notes that format as they are typed, edited live over the extension's Yjs protocol; wiki links, embeds, images and attachments; sketches, drawn with the web editor's rasterizer ported rule for rule so a stroke looks the same on every client; links to notes from task descriptions. |

Two parts of Design Docs follow the web editor closely enough to be worth knowing how:

- **Live formatting.** A note is one surface, as on the web: it reads as what its Markdown means, a tap in the text starts typing there, and putting the keyboard away ends it — there is no edit mode. Underneath it is the note's exact Markdown in a `UITextView`, which is what keeps it bound to the shared document character for character. `LiveMarkdown` parses the text with swift-markdown — the same CommonMark and GFM grammar the web editor's parser implements — and says what each run is; `NoteStyler` turns that into attributes and applies only the ones that changed. Syntax is folded away by styling it to nothing, never by removing it, and comes back when the caret touches its span (for a heading or a quote, its line; for a code block's fences, anywhere in the block). A custom layout manager draws what attributes can't: a quote's bar, a code block's background, a bullet in place of a list marker's glyph, and a task's box. A task — `- [ ]`, `- [x]` — is drawn as a round mark in place of all of that, empty or filled and ticked as Notes' checklists are, the same on a phone, an iPad and a Mac; a tap or a click on the box ticks or clears it by changing the character between the brackets, whether or not the note is being typed in, and leaves the caret where it was; the caret brought into the box — anywhere up to its closing bracket — shows it as the text it is, to be changed or taken out by hand. (The web's editor shows a task as its text and nothing more.) While the note isn't being typed in, a tap on a link follows it.
- **Pictures.** A line holding nothing but embeds is a row: one print, or several fanned into a stack with the web's own tilt for each path. Tapping opens them full screen with the system zoom transition, to swipe between, edit (a sketch), replace (an image), share, remove from the note or delete. The reader and the editor draw rows with the same view; in the editor it is hosted over a line made exactly as tall as the row.

- **Carets and pens.** Who is where travels over Yjs's awareness protocol, as on the web (`Awareness.swift`): a caret in a note, a pen and the stroke it is in the middle of on a sketch, each in the colour the instance gave that person. A caret is sent as the identity of the character it stands before, so that it holds its place while text is typed around it — and YSwift does not expose the document structure that turns that into an offset. `YjsStructure.swift` reads it out of the document's own update encoding and orders it with Yjs's rule for concurrent insertions. It is used for carets and nothing else, and it checks the text it reconstructs against the document's before placing one.
- **Moving a sketch's page** is the web editor's arithmetic (`SketchViewport.swift`, from `js/sketch/viewport.js`): a pan, a zoom and an angle, worked out from the raw touches so that what was under two fingers when they landed is under them still — they carry the page, zoom it and turn it, with no recognizer's threshold in between. A button puts it back, upright and fitted. Two fingers tapped together undo and three redo, as on the web; a finger draws unless Settings keeps drawing for the Pencil (or the Page menu says otherwise), and then one finger moves the page, as on the web. A trackpad scrolls, pinches and turns it too, and with Command or Option held its scroll zooms or turns.
- **Looking closer at a picture** is a scroll view's zoom (`ZoomablePicture.swift`), which keeps the place between the fingers where it is; a double tap zooms in on the place tapped.
- **Undo in a sketch** is Yjs's undo manager over the same parts of the document the web editor's watches, so it takes back a stroke, a change of paper or a cleared page, and never anybody else's work. Clearing plays the web's explosion, which the app fetches from the extension's content on the instance rather than carrying a copy.

### Extensions with no native half

Any other extension the instance runs still works here. Its manifest's `nav` entries are listed where the web's sidebar lists them — per project on the project's overview and in the sidebar, once on the Account tab for an instance-level page. Opening one draws the page natively when it is built from the kit, which is covered further down, and otherwise shows that page of the instance's web client inside the app's own bars (`Extensions/Web`).

The web client knows when it is hosted this way (`HostShell` in `Solo.Client`) and does three things differently:

- **It is only the page.** No app bar, no navigation, no footer, and no background of its own, so the app's shows through.
- **It signs in with a session issued for it, not with the app's.** The app's session lasts a month and is renewed by use, and a page keeps what it is handed where its scripts can read it. So the app asks the instance for a stand-in (`POST api/auth/sessions/hosted`, `HostedCredential.swift`): the same person for an hour, which nothing can extend or turn into another credential, and which stops with the app's session. The app asks for the next one three quarters of the way through and puts it where every page that is up reads it, so a page never sees one end; when the app comes forward after longer than that away, it does the same before the pages find out. No provider is involved, whichever the instance uses. A session the API refuses is reported to the app, which checks its own session for itself before signing anyone out, and otherwise hands the page a fresh one and loads it again. An instance from before hosted sessions has no such address, and its pages are handed the app's session as they were.
- **Links to screens the app has go to the app.** The app tells the page which addresses it owns — a board, a project, a baked-in extension's page where that extension is installed — and a link to one opens the native screen. Anything else is the extension's and stays in the page; a link off the instance opens in the browser.

The page is given nothing of the device and can ask the app for nothing: it runs as web content, and what it may tell the app is that it is up, that its session was refused, and where it would like to go.

**What such an extension adds to core's own screens** — a section on a project, a badge on a card — is drawn natively when it is built from the kit (`Solo.Shared.Kit`, contract 1.17), and not shown otherwise. The app cannot run the extension's code, so the code runs where it always does: one page of the web client, kept in a web view nobody sees for the whole session (the client's "kit surface"; `Extensions/Web/KitSurface.swift` here). The app asks it to mount a place; the page runs that place's contributions with the parameters core gives them and describes the kit components they render as a tree of nodes; the app draws the nodes with its own controls. A press goes back as a click on the node it came from, so the extension's handler answers it, and whatever changes comes back as a new tree.

- **Places:** every one the web client has. A project's card, overview, sidebar group and settings; Your Tasks and its cards; a board's cards, column headers and settings; a task's detail and its menu; an extension's panel in Admin → Extensions; and the app bar, which here is a row above the Account tab's extension links.
- **A task's menu** is the one place that is not components: an extension answers with items, and the app shows them in a menu of its own beside Move and Delete in the task's detail. A card's press-and-hold menu does not have them — that would mean asking the page about every card.
- **Dialogs and snackbars.** A contribution may open one of the web client's dialogs — the task picker, a confirmation — which the app cannot draw. While one is up, the page itself is shown in a sheet, with nothing on it but the dialog; closing the sheet closes the dialog. What a contribution says in a snackbar is said as one of the app's own toasts.
- **Cards are for reading.** A card is one button, so what an extension puts on it is shown and cannot be pressed.
- **Writing and picking.** A kit text field is the app's own field. What is written goes to the extension when the writing pauses and when the field is left; while it is being written in the field is the person's, and once it is left it shows whatever the extension kept. A kit picker is a menu, and shows what the extension says is picked.
- **Only data crosses.** A node is a kind and some text; a press, something written and something picked are all that go back. `Href` on a row or a button opens the app's own screen where it has one, and the web client's page otherwise.
- **It runs only when it could matter.** The page starts the first time a place is shown on an instance that has such an extension, and closes for good if it reports that none of them contributes anything. The system ending its process restarts it, twice at most; a memory warning with nothing mounted closes it until it is next needed. It sits in the window at one point square, because out of a window the system holds its timers back.
- **A baked-in extension is never drawn this way.** The page is told which extensions the app has native halves for and leaves them out.

**An extension's own page** is asked of the same hidden page first (`PluginPageView`). The web client finds the page for the address, runs it, and says who draws it:

- **The app**, when everything the page renders is a kit component. It is drawn as a screen: text at a screen's size, a stack of nothing but rows as a glass panel, buttons as the app's own glass buttons, pull to refresh starting the page over.
- **The web client**, in a web view as before, when the page is marked `[WebPage]`, reads a query string, or is not an extension's page at all. The app is told at once and never tries to draw it.
- **The web client, after a moment**, when an unmarked page turns out to render something that is not the kit. The app switches to the web view when it is told, and does not switch back.

Nothing is waited for that could not answer: with no kit surface — it failed, the instance's web client is older than this, nothing on the instance has a page — the page is the web's straight away. A link from a page shown in a web view to a page the app could draw stays in the web view, drawn by the web client: only the app's own list of screens is handed to a hosted page.

About names the extensions this applies to. In a debug build the surface's timings and message sizes are written to `Documents/kit-surface.json`.

`Spikes/NativeKit` is a plugin for trying all of this, with pages and a kit contribution for each place, and `SOLO_OPEN=web:<path>` opens any address of the web client's this way. `SOLO_WEB_EXTENSIONS=mcp` lists a baked-in extension's manifest pages from the web as well.

## Where it differs from the web client

Better here:

- With the instance out of reach, opens to what can still be worked on — the design docs on the device — rather than to pages that can only be read.
- A task's detail sits beside its board on an iPad instead of over it.
- On a phone, a board's epics stay lined up across its columns, and a moved card is followed to where it lands.
- A card, a lane or a group that is dragged is picked up as itself, and the rows it is carried over part to make room for it; lanes fold while one is carried.
- Sketches take Apple Pencil pressure, and a double-tap on the Pencil swaps pen and eraser.
- Notes and folders are moved by dragging them about the tree, and a note dragged into a note being written becomes a link to it.
- Home Screen widgets, and haptics for picking a card up, putting it down and clearing a sketch.
- The theme is picked up on returning to the app, without a reload.

Not here — use the web client for these:

- **First-run setup** of a new instance. The wizard needs the identity provider's ID token, which the app never holds; it sends you to the instance's `/setup` page.
- **Design Docs:** importing and exporting an Obsidian vault as a zip (a downloaded design doc's recovery archive is the one zip there is — see "A design doc can be downloaded" — and its sketches are drawn without their text boxes, as they are everywhere here); dragging pictures between rows; and, in sketches, text boxes — which are **not drawn at all**, so a sketch with text on it shows without it, though clearing the sketch removes them and Undo brings them back — and the selection, lasso and shape tools. Tables and inline pictures are shown as their Markdown rather than drawn.
- **Third-party extensions' screens**, for the reason above.
- **Notifications, without push.** Nothing is registered with Apple and the instance has nothing to send through, so the app does what a device can do alone (`Core/Notifications`). None of it leaves the instance or the device.
  - **Deadline reminders are scheduled ahead.** The instance lists the ones it will raise and when (`GET api/notifications/upcoming`), and the app hands them to the system to show at that time, open or closed, on a Mac too. They are replaced after every look at the inbox, soonest first, at most 60 pending across all instances, since the system drops anything past 64 without a word.
  - **The inbox is announced when the app hears of it.** Over the live connection while it runs: a toast in front, a notification on the device behind another app. On an iPhone or iPad a background refresh (`BackgroundSync`, a `BGAppRefreshTask` named `<bundle id>.refresh`) reads every signed-in instance when iOS chooses — at most every 15 minutes, in practice a few times a day, and never after the app was swiped away until it is opened again. A Mac has no such refresh; the instances that aren't showing are read every five minutes while the app runs, there and on iOS.
  - **Nothing is said twice.** Whoever is about to announce an entry asks `DeviceNotifications.claim` first, which records what the device has seen for each instance. A deadline entry counts as said when this device showed the reminder it was raised from (`NotificationDto.Key`); one that arrives before its reminder takes the reminder down instead. With the app in front a reminder stays quiet, and the toast for its entry says it.
  - **A tap opens its task**, on the instance it came from: the app turns to that instance first if another is showing.
  - Signing out, removing an instance, or an instance answering 401 takes its reminders and its record with it. An instance from before `api/notifications/upcoming` simply has no reminders scheduled.
  - To run a refresh by hand on a device, pause a debug build in Xcode and enter `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.hunterahlquist.solo.native.refresh"]`, then continue. The simulator doesn't run background tasks.

## Several instances

The app keeps any number of instances and shows one. Each has its own session, in the Keychain under its address, so going from one to another signs nobody out and asks nobody to sign in: the one that was showing has its live connection put down, and the next is opened with the session it already has. What an instance is — its provider, its theme, its extensions — is read from it each time it is shown, so two instances that sign in differently are no different to the app; an address signs in through its own `/desktop-auth` page, once, when it is added.

- **Where they are.** On an iPhone and an iPad, a list on the Account page: the one showing ticked, a tap to change, a swipe to remove, and Add Instance. An iPad's sidebar title — the instance's name — is a menu of them as well, once there is more than one. On a Mac they are a section of the Settings window and **File ▸ Switch Instance**, the first nine on ⌃1 to ⌃9. The sign-in page, and the pages that say an instance can't be reached or isn't set up, have the same menu, so a signed-out or unreachable instance is never a dead end.
- **Adding one** asks the address whether it answers before anything is left for it (`AppModel.probe`), in a sheet over whatever is showing: a mistyped address costs nothing.
- **Removing one** revokes its session on that instance, and drops the token, the cached answers and the theme kept for it. Its address stays under Recent in the sheet.
- **What isn't showing isn't live.** Only the instance showing has a hub connection. The others are asked for their unread count when the app comes forward, when the instance showing changes, and every five minutes; the total is the badge on the Account tab (an iPad's account row, a Mac's Instances row in Settings and its menu). A notification on an instance that isn't showing raises no banner.
- **What is kept apart.** The theme (so an instance's first frame wears its own, not the last one's), the response cache, and the sidebar's project order and recents, each by address. The colour scheme preference is the device's.
- **Widgets** show the instance that is showing in the app.
- **One at a time, on a Mac too.** The desktop shell gives each instance a window; here there is one window and one session, and the instance is changed in it.

## Signing in

The app uses the same handshake as the desktop shell: it asks the instance to start a sign-in (`POST api/auth/desktop/start`), opens the instance's `/desktop-auth` page in an `ASWebAuthenticationSession`, and redeems the code that comes back for a session token, with PKCE throughout. The redirect lands on a loopback listener the app opens for the duration.

It first tries `POST api/auth/desktop/start-app`, the endpoint the Capacitor app's branch adds for returning to an app by its own URL scheme (`com.hunterahlquist.solo`), and falls back to the loopback flow when the instance doesn't have it — so it works against `main` today and will use the better path once that lands.
