# Electron Liquid Glass in Solo Desktop

Research date: August 20, 2026

## Conclusion

Yes, Solo can load `electron-liquid-glass` even though its renderer is Blazor WebAssembly. The add-on runs in Electron's Node.js main process, receives the native `NSView *` returned by `BrowserWindow.getNativeWindowHandle()`, and does not depend on the renderer framework. Electron explicitly supports native add-ons that create native UI, and documents the macOS native window handle as an `NSView *`. ([Electron native code](https://www.electronjs.org/docs/latest/tutorial/native-code-and-electron), [Electron `getNativeWindowHandle`](https://www.electronjs.org/docs/latest/api/browser-window#wingetnativewindowhandle))

There is an important qualification. The package can provide a native glass **backdrop**, but version 1.1.1 does not integrate `NSGlassEffectView` the way Apple recommends for content. Apple says to put the content in `NSGlassEffectView.contentView` so AppKit can apply legibility treatments, and explicitly says not to place the glass view behind the content as a sibling. The package does exactly the latter: it inserts an `NSGlassEffectView` below Electron's renderer view and never assigns `contentView`. ([Apple WWDC25 guidance at 18:13](https://developer.apple.com/videos/play/wwdc2025/310/?time=1093), [Apple `contentView` documentation](https://developer.apple.com/documentation/appkit/nsglasseffectview/contentview), [upstream insertion code](https://github.com/Meridius-Labs/electron-liquid-glass/blob/main/src/glass_effect.mm#L88-L200))

Therefore, this package is reasonable for a visual prototype or backdrop effect. A production claim of fully native, AppKit-correct Liquid Glass would require testing the result carefully and probably forking or replacing the native integration so the Electron content view is wrapped as the glass view's `contentView`.

## Compatibility with Solo

- The package documents macOS 26 or later for true Liquid Glass, Electron 30 or later, and Node.js 22 or later. Solo currently uses Electron `^43.4.1`; Electron 43 embeds Node.js 24.17, and Solo's desktop CI uses Node.js 24, so those runtime floors are satisfied. On earlier supported macOS versions, the add-on source dynamically falls back to `NSVisualEffectView`, which is legacy vibrancy rather than Liquid Glass. ([upstream requirements and fallback](https://github.com/Meridius-Labs/electron-liquid-glass#requirements), [upstream fallback implementation](https://github.com/Meridius-Labs/electron-liquid-glass/blob/main/src/glass_effect.mm#L140-L190), [Electron 43 stack](https://www.electronjs.org/blog/electron-43-0), [Solo package](../../src/Solo.Desktop/package.json))
- The published 1.1.1 package contains Node-API prebuilds for both `darwin-arm64` and `darwin-x64`, matching Solo's separate `--arm64` and `--x64` macOS artifacts. Node-API is ABI-stable across Node.js versions, which makes the prebuilds materially safer across Electron upgrades than a V8-bound add-on. Both packaged architectures still need launch tests. ([arm64 prebuild](https://cdn.jsdelivr.net/npm/electron-liquid-glass@1.1.1/prebuilds/darwin-arm64/), [x64 prebuild](https://cdn.jsdelivr.net/npm/electron-liquid-glass@1.1.1/prebuilds/darwin-x64/), [Node-API stability](https://nodejs.org/api/n-api.html), [Solo release workflow](../../.github/workflows/release-desktop.yml))
- Avoid forcing a source rebuild unless needed. The upstream `binding.gyp` still selects C++17, while Electron requires C++20 when rebuilding native modules for Electron 33 and later. The shipped Node-API binaries avoid that mismatch; a source-build fallback may need an upstream or local build fix. ([upstream `binding.gyp`](https://github.com/Meridius-Labs/electron-liquid-glass/blob/main/binding.gyp#L17-L22), [Electron 33 native-module change](https://www.electronjs.org/blog/electron-33-0#behavior-changed-native-modules-now-require-c20))
- The published package declares `os: ["darwin"]`. Solo also builds on Windows and Linux, so it should be an `optionalDependency`, loaded only inside a guarded `process.platform === "darwin"` branch with absence handled. npm documents optional dependencies specifically for dependencies whose failed or unsupported install must not fail the whole installation. ([published package metadata](https://cdn.jsdelivr.net/npm/electron-liquid-glass@1.1.1/package.json), [npm package metadata rules](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#optionaldependencies))

## Integration point

The change belongs in the existing Electron shell, not in Blazor interop:

1. Conditionally load the add-on in [`src/Solo.Desktop/main.js`](../../src/Solo.Desktop/main.js) on macOS.
2. Construct the main `BrowserWindow` with `transparent: true` and no Electron `vibrancy` option. The upstream module calls transparency mandatory and warns that Electron vibrancy conflicts with the effect. Electron also documents that transparency must be selected in the window constructor. ([upstream quick start](https://github.com/Meridius-Labs/electron-liquid-glass#basic-usage), [Electron transparent windows](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles#transparent-windows))
3. After the renderer finishes loading, call `addView(mainWindow.getNativeWindowHandle(), options)` and keep the existing `hiddenInset` title bar. Explicitly keeping the traffic lights visible is compatible with Solo's current custom title-bar layout. ([upstream API](https://github.com/Meridius-Labs/electron-liquid-glass#liquidglassaddviewhandle-options), [Electron traffic-light API](https://www.electronjs.org/docs/latest/api/browser-window#winsetwindowbuttonvisibilityvisible-macos))
4. Make only the intended macOS desktop regions transparent or translucent in the renderer CSS. Solo currently paints an opaque root background and opaque MudBlazor page backgrounds, so the native view would otherwise be hidden. This is ordinary CSS/theming work in the Blazor client, not a .NET or JavaScript interop limitation. ([Solo desktop CSS](../../src/Solo.Client/wwwroot/css/app.css), [Electron transparent-window model](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles#transparent-windows))

The package creates one native view covering the Electron content bounds. It cannot turn individual MudBlazor cards or controls into separate native `NSGlassEffectView` instances. Any card-level glass appearance would still be rendered by Chromium/CSS over the native backdrop.

## Signing, notarization, and production risk

- The `.node` file is executable nested code. It must be included as a production dependency, unpacked from ASAR, architecture-matched, and signed before notarization. electron-builder normally includes production dependencies, rebuilds native dependencies per target architecture, and smart-unpacks native modules, but the packaged app should be inspected because native modules are the failure-prone case. ([electron-builder contents and smart unpack](https://www.electron.build/docs/contents/), [electron-builder native build phase](https://www.electron.build/docs/features/build-lifecycle/), [Electron native-module guidance](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules/))
- Solo already enables hardened runtime, provides the Electron JIT/WASM entitlements, and requests notarization. The add-on only links AppKit and does not appear to require a new protected-resource entitlement. Do not add `disable-library-validation` merely to make an unsigned binary load. Apple requires all distributed executables to be signed, hardened, and securely timestamped, and in-process plug-ins inherit the host process's entitlements. ([Solo macOS packaging](../../src/Solo.Desktop/package.json), [Solo entitlements](../../src/Solo.Desktop/build/entitlements.mac.plist), [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution))
- `NSGlassEffectView` is now a documented public AppKit class. However, the package's `unstable_setVariant`, `unstable_setScrim`, and `unstable_setSubdued` methods deliberately invoke private setters, and upstream says not to use them in production. Solo should use only the stable `addView` options. ([Apple `NSGlassEffectView`](https://developer.apple.com/documentation/appkit/nsglasseffectview), [upstream experimental API warning](https://github.com/Meridius-Labs/electron-liquid-glass#undocumented-experimental-methods))

## Recommendation

Prototype the stable `addView` path behind a macOS-only feature flag, with the package optional and the CSS changes gated by Solo's existing desktop/macOS classes. Accept it only after testing macOS 26 on Apple silicon and Intel, an older macOS fallback, Reduce Transparency, active/inactive windows, resize/fullscreen, and the signed/notarized DMG and ZIP. Apple also recommends testing custom glass with accessibility transparency and motion settings. ([Apple adoption guidance](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass))

If visual fidelity and native legibility behavior are requirements, treat the upstream sibling-view design as the blocking issue and change the native layer to wrap Electron's content in `NSGlassEffectView.contentView` before shipping.
